# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Small Rails 8.1 app (Ruby 3.3.4, PostgreSQL) with two jobs. It bridges Workbench projects to QuickBooks Online: given a project name, it finds the matching QuickBooks customer and returns its invoice. It also produces the weekly platform-engagement report, segmenting every petasos client from petasos and thoth data. The README is the unmodified Rails stub.

## Commands

- Setup: `bundle install && yarn install`, then `bin/rails db:setup`
- Dev server (Rails + JS/CSS watchers): `bin/dev` (runs `foreman start -f Procfile.dev`)
- One-off asset builds: `yarn build`, `yarn build:css` (output goes to `app/assets/builds`, which is gitignored)
- Report: `bin/rails report:weekly[YYYY-MM-DD]` runs the week containing that date (default: the week that ended yesterday), records it in `account_weeks`, writes `tmp/reports/segments-<monday>.csv` and emails it. `last_login` is overwritten on every login, so past weeks can't be rebuilt accurately.
- Tests: `bundle exec rspec`; single file/example: `bundle exec rspec spec/requests/invoices_spec.rb:12`. Run the asset builds first, because `spec/requests/layout_spec.rb` expects built, digested assets. The suite needs the `workbench_admin_petasos_test` and `workbench_admin_thoth_test` databases (`db:test:prepare` loads them from the hand-written `db/petasos_schema.rb` and `db/thoth_schema.rb`). Specs block network access (WebMock, localhost allowed) and reset the memoized `IntuitAccount.instance` before each example.
- Lint: `bundle exec rubocop` (rubocop-rails and rubocop-rspec; double-quoted strings enforced; Bundler/OrderedGems is off)
- Deploy: Capistrano (`bundle exec cap staging deploy` / `cap production deploy`), from `main`, to the hg-packer AMI. `capistrano-hgpacker` restarts Passenger as the systemd unit `passenger@workbench-admin`. Staging (`cap staging deploy`) runs Postgres on the box, creates its database on first deploy, and reads `config/credentials/staging.yml.enc`; its key (`config/credentials/staging.key`, gitignored) lives in the Secrets Manager secret `workbench-admin/credentials/production` under `staging`. `config/schedule.rb` (whenever, installed by `cap deploy`) refreshes the Intuit tokens every Wednesday so an idle app stays connected and runs `report:weekly` on Mondays at 06:00. (The old Sunday Passenger restart only re-read the Let's Encrypt certs; TLS now terminates at the ALB.)

## Architecture

### Weekly segment report

- **Multi-database:** `primary` is this app's own database. `petasos` and `thoth` are read-only connections to the other apps' databases, through the abstract `Petasos::Record` and `Thoth::Record` models (`app/models/petasos`, `app/models/thoth`). Outside test they set `database_tasks: false` and a non-existent `migrations_paths`, so primary migrations never run against them. Production and staging take their URLs from `databases.petasos` and `databases.thoth` in the credentials, and the roles on the RDS instances must be read-only.
- **`SegmentReport`** (`app/interactors`) builds one `Row` per petasos client. Users are matched across systems by lower-cased email. Precedence is Power (any Ask MercuryAI report) > Activated (any other report) > Active (a member's `last_login` in the week) > Dormant. A petasos project belongs to its client through `projects.domain_id`, not `account_id`. Finished reports in thoth are `deliverable: true`, status `ready`, and the Ask models come from `metadata->>'model'` (`Thoth::Completion::ASK_MODELS`).
- **`AccountWeek`** stores each week's row, keyed by client and the week's Monday, so the next run can report `segment_change` (nil with no earlier row). `SegmentReport.csv` prefixes cells that start with `= + - @` so spreadsheets don't run them as formulas. `ReportMailer.weekly` sends the CSV; it needs the petasos `smtp` credentials block, and recipients come from `ApplicationConfig.report_recipients`.

### QuickBooks invoices

- **Flow:** `InvoicesController#show` (`GET /invoices/:id`, where `:id` is the project name) → `before_action :acquire_token` → `LocateInvoiceForProject` interactor (`app/interactors`, `interactor-rails` gem) → QuickBooks via `quickbooks-ruby`. The interactor first queries Customer by `DisplayName LIKE "<project_name> %"` with `MAXRESULTS 2`. It fails with `:not_found` for 0 matches and `:ambiguous` for more than 1. It then looks up the customer's invoices and fails with `:not_invoiced` if there are none. The controller maps `:ambiguous` to 409 and every other failure to 404. A success renders the customer name as plain text.
- **OAuth lives in `ApplicationController`:** it holds the Intuit auth actions (`intuit_authenticate`, `intuit_callback`), and `GET /api/oauth_callback` routes to `application#intuit_callback`. If there is no stored access token, `acquire_token` redirects to Intuit's grant URL. The callback saves the token and redirects back to `invoice_path(session[:target])`. `intuit_authenticate` is not currently routed.
- **Token storage:** `OauthToken` (single-table inheritance via `type`, unique per type) includes `QuickbooksOauth` (`app/models/concerns`), which holds the OAuth2 client, grant URL, and refresh logic. `IntuitAccount` is the singleton row (`IntuitAccount.instance`). `with_token` yields an `OAuth2::AccessToken`, refreshing and retrying up to 3 times on `OAuth2::Error` or `Quickbooks::AuthorizationFailure`, then raises `TooManyRetries`.
- **Config and secrets:** read them only through `ApplicationConfig` (`lib/application_config.rb`, values in `config/application_config.yml`) and `ApplicationSecrets` (`lib/application_secrets.rb`, over the encrypted credentials), so they can move out of the repo later. A lint spec fails on any other `Rails.application.credentials` access. Both are required early in `config/application.rb` because `database.yml` uses them. Add a new value as an accessor on the right module.
- **Credentials:** one Intuit app per environment (client id, secret, realm), read through `ApplicationSecrets`. `config/credentials/production.yml.enc` holds the live app; `config/credentials/{staging,development,test}.yml.enc` hold the sandbox app and set `intuit_app: sandbox`, which also turns on `Quickbooks.sandbox_mode` and the sandbox discovery document. Each file has its own gitignored key and its own Active Record encryption keys. `config/initializers/quickbooks.rb` also sets an unused `intuit_realm`.
- **Frontend:** Hotwired (Turbo and Stimulus), esbuild via jsbundling-rails and Bootstrap via sass (cssbundling), both writing to `app/assets/builds`, served by Propshaft. Slim templates. It is nearly empty; `IntegrationController` only serves the QuickBooks TOS and privacy pages (`app/views/integration`). `/` redirects to researchresultswebsite.com.
- **Gem pin:** `quickbooks-ruby` is held at `~> 1.0` (2.x moves to oauth2 2.x). Rails and Ruby versions are pinned in `Gemfile`, `.rubocop.yml` and `config/deploy.rb` (`rbenv_ruby`), so the deploy host needs that Ruby (Fullstaq `-jemalloc` build in `deploy.rb`). Rails upgrade conventions and intentional config are logged in `doc/rails-upgrades.md`.
